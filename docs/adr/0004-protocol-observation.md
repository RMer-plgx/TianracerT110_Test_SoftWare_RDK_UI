# ADR-0004. 探索底盘协议观测

## 状态

Proposed。协议旁路已实现（**代理桥接，不是只嗅探**，见下一节），并取得一次架空状态下的实车采集证据（见「实现与验证进展」）。采集可行性已部分验证；链路影响、运动状态、数据解释完整性和交付策略仍待确认，是否列为必检尚未确定。

## 背景

传感器运行数据主要通过 ROS 话题获取。话题无数据时，仅凭 ROS 结果不能区分请求未发出、设备未响应或数据解析发布失败。此前有限时间的被动采样未观察到预期电压响应，采样条件及原始记录需回查，不能据此断定话题永不发布或车端缺少查询逻辑。

## 实现选择：从「只嗅探」偏离到「代理桥接」

决策正文写的是「被动采集不写串口」，但**当前实现是代理，不是嗅探**。
这个偏离必须显式记录，不能靠读代码才发现。

| 方面 | 只嗅探（决策原文） | 代理桥接（实际实现） |
| --- | --- | --- |
| 数据通路 | 真串口仍归底盘节点，另开一路旁听 | 真串口归桥接进程，底盘节点读写 pty |
| 是否写串口 | 否 | **是**（`_to_mcu` → `ser.write`） |
| 桥接挂掉 | 不影响控制 | **控制链路中断** |
| 能否不改车端源码 | 通常需要驱动配合 | 能，靠改环境变量指向 pty |

**选择代理的理由**：单串口场景下，两个进程不能同时读同一个 tty（先读者把数据拿走）。
不改车端源码又要在串口上分出一份数据，只能把串口让给中间层代转。
`probes/serial_tap.py` 顶部注释「不改任何车上源码」指的就是这一点。

**代价（已知且未完全消除）**：

1. 桥接是控制链路单点。它挂掉时，**已经发给 MCU 的运动指令不会自动撤销**。
   是否停车取决于 MCU 固件的通信超时保护，而该行为**尚未确认**。
   旧版注释写的「退出即安全」是错的，已更正。
2. 实现上必须保证「转发循环绝不阻塞」，否则会出现「进程活着、链路已死」
   而上位机发现不了的状态。当前已改为非阻塞写 + pending 队列 + 看门狗。
3. 因此采集期间**车辆必须架空且不得运动**，这是硬约束，已写进
   `tools/tap_probe.py` 的用法说明与运行时提示。

**替代方向（未实现，供后续取舍）**：USB 层嗅探（usbmon）不改串口归属，
是真正的旁观者；代价是需要 root、需解析 USB 封装而非串口字节流。

## 决策

候选方向是在 ROS 检测之外，增加独立的底盘协议观测，用于补充链路证据：

- 保留 ROS 原始观测及判定，单独记录协议采集结果和可信度；采集失败、丢帧或覆盖不足须标记未验证，不能静默当作通过。
- 先核实实际设备路径、串口独占方式、RX/TX 可观测性及采集完整性；重复打开设备或使用某个转发工具本身不能证明可以无干扰旁路。
- 核对适用固件的帧格式、字段、校验和触发条件。只有可靠覆盖发送侧且了解查询周期和触发条件，才能说明采集窗口内未见请求；不能据此直接断言代码缺少查询逻辑。
- 被动采集不写串口；主动查询是独立操作，需要明确授权、限定频率与时长，并准备停止和恢复路径。先用模拟环境验证，再在授权下验证实车和对现有链路的影响。
- 是否将协议观测列为必检及其对交付的影响按产品和阶段确认；非必检时可继续 ROS 检测，但报告应说明证据限制。

## 替代方案

- 仅使用 ROS 话题：改造成本低，但难以定位链路层的数据缺失和解析问题。
- 未验证就直接复用或重复打开串口：可能无法获取双向完整数据，也可能干扰现有控制链路。

## 影响

需要协议资料、采集覆盖及可靠性证据，并明确不同车型和异常状态的处理。即使采到帧，也不能自动证明物理链路完整或推断未观测到的行为。

| 项 | 结果 |

| 双向可观测性 | 两个方向均可落盘（下行 447929 B、上行 2286 B） |

| 帧格式 | 仅两种帧长：47 B（里程计/IMU）与 11 B（电压），逐帧验证「总长 = len + 5」成立；上行 9 B（心跳）同样成立 |
| 电压回传 | 60 s 收到 6 帧 `Voltage_RESPONSE`，11.48 ~ 11.52 V；上行无电压查询帧 |

半帧错位同源。修复桥接的半帧处理与非阻塞转发后，2026-11-07 那次为 0。

### 由此订正的一条判断

背景中「未观察到预期电压响应」在实车采集中不成立：**下位机会主动低频上报电压**。
20 s 出现 3 帧、60 s 出现 6 帧，位置不规律。ROS 层短窗口订阅抓不到，
属于「发得太稀」，不能据此推断「话题永不发布」。

同理，未见电压查询帧也不足以断言车端缺少查询逻辑或触发条件 ——
采集窗口、查询周期和触发条件仍待确认。

### 尚未验证

**阻塞项（未确认前不得接入正式流程）**：

- **MCU 是否具备通信超时保护** —— 即「持续 N 毫秒未收到合法帧就自动停车」。
  这决定了桥接挂掉时车会不会自己停。从 ROS 驱动源码只能确认：
  上位机的 `communication_timer_` 只打日志（`core.cpp:130-133`），
  不发停车指令，所以兜底完全依赖下位机固件。
  确认方式：架空实验（发低速前进 → `kill -9` 桥接 → 观察是否自停）。

其他未验证：

- 旁路对现有控制链路的影响：延迟、丢帧、底盘稳定性，未做运动测试
- 任何运动状态下的采集
- 不同车型、不同固件版本的帧格式与包类型一致性
- 采集失败、部分丢帧时的降级与标记行为

### 旧数据不能被当成本次结果

第 20 项读的是车上日志文件，而**文件存在不代表本次采过**：
手动跑过一次采集、或采集异常退出，上一次的数据会留在目录里。

因此本项由 `ros.tap.enabled` **显式开关**控制（默认 `false`）：

- 开关关闭 → 直接 SKIP，**不去读文件**，连 SSH 探测都不发
- 开关开启但车上无数据 → SKIP，注明「未取得数据不能计为通过」
- 开关开启且有数据 → 才按本次数据判定

2026-11-07 在真车上验证：往 `/tmp/tap` 摆放 9535 帧健康数据、
开关保持 `false`，第 20 项返回 SKIP 且无任何 measurement。
同时确认采集结束后车上日志目录已被清除、无残留进程。

### 当前实现边界

旁路仅作为独立命令行验证工具存在（`tools/tap_probe.py` + `probes/serial_tap.py`），**未接入 GUI/CLI 正式检测流程**。检测项第 20 项在未启用采集时判 SKIP，不参与交付判定，因此当前对交付结论没有影响。

不接入的原因不是「没做过运动验证」这个措辞，而是上面那条阻塞项：只要 MCU 超时行为未确认，桥接就不该进默认路径。

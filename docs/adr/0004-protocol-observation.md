# ADR-0004. 探索底盘协议观测

## 状态

Proposed。协议旁路已实现，并取得一次架空状态下的实车采集证据（见「实现与验证进展」）。采集可行性已部分验证；链路影响、运动状态、数据解释完整性和交付策略仍待确认，是否列为必检尚未确定。

## 背景

传感器运行数据主要通过 ROS 话题获取。话题无数据时，仅凭 ROS 结果不能区分请求未发出、设备未响应或数据解析发布失败。此前有限时间的被动采样未观察到预期电压响应，采样条件及原始记录需回查，不能据此断定话题永不发布或车端缺少查询逻辑。

## 决策

候选方向是在 ROS 检测之外，增加独立的底盘协议观测，用于补充链路证据：

- 保留 ROS 原始观测及判定，单独记录协议采集结果和可信度；采集失败、丢帧或覆盖不足须标记未验证，不能静默当作通过。
- 先核实实际设备路径、串口独占方式、RX/TX 可观测性及采集完整性；重复打开设备或使用某个转发工具本身不能证明可以无干扰旁路。
- 核对适用固件的帧格式、字段、校验和触发条件。只有可靠覆盖发送侧且了解查询周期和触发条件，才能说明采集窗口内未见请求；不能据此直接断言代码缺少查询逻辑。
- 被动采集不写串口；主动查询是独立操作，需要明确授权、限定频率与时长，并准备停止和恢复路径。先用模拟环境验证，再在授权下验证实车和对现有链路的影响。
- 是否将协议观测列为必检及其对交付的影响按产品和阶段确认；非必检时可继续 ROS 检测，但报告应说明证据限制。

## 替代方案

- 仅使用 ROS 话题：改造成本低，但难以定位链路层的数据缺失和解析问题。
- 未验证就直接复用或重复打开串口：可能无法获取双向完整数据，也可能干扰现有控制链路。

## 影响

需要协议资料、采集覆盖及可靠性证据，并明确不同车型和异常状态的处理。即使采到帧，也不能自动证明物理链路完整或推断未观测到的行为。

## 实现与验证进展

2026-11-06 在 Tianracer T110 RDK 测试车（`192.168.128.10`，`/dev/ttyUSB0`，115200）以架空状态被动采集 20 秒。原始字节存档于仓库外的 `.codewhale/evidence/20261106_proto/`。

### 已验证

| 项 | 结果 |
| --- | --- |
| 串口旁路方式 | 底盘节点串口路径由环境变量决定，改指 pty 即可旁路；未修改车端源码 |
| 双向可观测性 | 上行 459 B、下行 116728 B，两个方向均可落盘 |
| 采集完整性 | 下行解析 2485 帧，帧头/长度校验失败 0，未知类型 0，bcc 错误 1（0.04%） |
| 帧格式 | 实测仅两种帧长：47 B（里程计/IMU）与 11 B（电压），与「总长 = len 字段 + 5」一致 |
| 电压回传 | 收到 3 帧 `Voltage_RESPONSE`，11.68 ~ 11.71 V；本次窗口内上行无电压查询帧 |

那条 bcc 错误帧的尾部紧跟下一帧帧头，与采集启停瞬间的半帧错位同源，不是帧长公式问题。

### 由此订正的一条判断

背景中「未观察到预期电压响应」在本次采集中不成立：**下位机会主动低频上报电压**，本次 20 秒出现 3 帧，位置不规律。ROS 层短窗口订阅抓不到，属于「发得太稀」，不能据此推断「话题永不发布」。

同理，本次窗口内未见电压查询帧，也不足以断言车端缺少查询逻辑或触发条件 —— 采集窗口、查询周期和触发条件仍待确认。

### 尚未验证

- 旁路对现有控制链路的影响：延迟、丢帧、底盘稳定性，本次未做任何运动测试
- 任何运动状态下的采集
- 不同车型、不同固件版本的帧格式与包类型一致性
- 采集失败、部分丢帧时的降级与标记行为

### 当前实现边界

旁路仅作为独立命令行验证工具存在（`tools/tap_probe.py` + `probes/serial_tap.py`），**未接入 GUI/CLI 正式检测流程**。检测项第 20 项在未启用采集时判 SKIP，不参与交付判定，因此当前对交付结论没有影响。

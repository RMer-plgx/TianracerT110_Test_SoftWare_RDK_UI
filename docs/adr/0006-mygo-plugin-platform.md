# ADR-0006. 使用 MyGo 桌面壳和产品插件构建多机器人检测平台

## 状态

Accepted（2026-11-07）。用户已确认按此方向编写技术方案，也未完成目标系统或实车验收。接口设计作为首轮实现基线，在分阶段计划的 P1 验证后冻结。

**实现进展：P0 探针已落地**（`platform/`，2026-11-07）。它**不是可用平台**，
只是对关键风险的可行性验证：

| 已实现 | 说明 |
| --- | --- |
| 插件包结构与完整性校验 | 路径安全、ZIP 限制、`integrity.json` 全文件覆盖 |
| 协议 v1 schema | 严格 JSON 解码（拒绝重复键、深嵌套、非有限数值） |
| JS/TS 沙箱 | MoeJS，新建 VM、禁动态代码、8MB 内存上限。入口可为 `.js` 或 `.ts`，按扩展名分别走 `moejs.Compile` / `moejs.CompileTS`（编译发生在 worker 内，包内不带预编译产物）；外部 import 被拒 |
| 一次性子进程探针 | 单次调用、超时、强制终止、取消与完成竞争已定义 |
| 原生界面 spike | MyGo，**仅样例数据，无设备连接** |
| 两个模拟插件 | `sim-base` / `sim-serial`，仅内存态能力 |

**尚未实现**：检测运行时会话与调度、设备能力与辅助程序、
证据归档、真实产品的插件化迁移、正式 UI、与现有 Python 程序的任何集成。

验证边界：P0 的检查已于 2026-11-07 在另一台 Windows 机器复验通过
（`go build` / `go vet` / `go test` / `go test -race` / 两个插件包校验 /
五项探针 / `schema-ts --check` 共 8 项）。**本仓库未有 CI 跑这些检查**，
换环境后仍需重新验证。

依赖风险（P0 阶段的已知不确定性）：

| 依赖 | 版本 | 风险 |
| --- | --- | --- |
| `MoeForge/moejs` | `v0.1.0-alpha.11` | **alpha 版本，而它是沙箱边界**。API 与隔离行为可能变。 |
| `egoist/mygo` | 伪版本 `v0.8.1-0.…-487bc3496d89` | 无 tag，靠 `go.sum` 锁定；上游删提交或 force-push 会拉不到。 |

以及 mygo 伪版本的上游可用性退路。

## 背景

后续要检测不同类型的机器人，其通信协议、检测流程、人工操作和判定标准都可能不同。产品扩展需要同时支持配置和代码，避免每新增一个产品就修改桌面程序。选型按新平台需求评估，NSH 是独立探索，其投入不计入决策成本，也不是新平台实施的前置条件。

参考 `egoist/mygo-music` 在提交 `8a366b7cc3363349d5eefdca448fc16f440a3dee` 的实现：MyGo 原生界面、JS/TS 插件、结构化页面、统一宿主能力和按需启动的辅助程序。播放器的超时、热替换和会话恢复语义需要针对检测场景重新设计。

## 决策

- MyGo 只承担桌面壳职责，首版使用 Go 原生 UI。检测运行时独立于 UI，负责会话、调度、资源占用、停止、恢复和证据归档；产品专属流程与判定进入插件。
- 产品插件以版本化包交付，包含声明、产品配置、基线、JS/TS 代码、交互描述和资源。已有能力组合形成的新产品应无需重新编译壳；需要新协议或厂商 SDK 时，通过受管适配器或辅助程序扩展。
- 产品脚本在独立 worker 中运行，检测运行时保留控制与停止通道。JS/TS 是默认扩展语言，原生辅助程序的语言按设备依赖选择。脚本引擎及框架版本在 P0 固定，采用 MoeJS 与否由所需 API、隔离和超时测试决定。
- 插件接口、消息、状态和权限采用独立版本。运行中的会话固定插件、配置和辅助程序内容；更新仅供后续会话使用。
- UI/UX 借鉴 `mygo-music` 的布局、视觉层次、主题和插件管理；检测停止、人工确认、未验证状态与证据查看使用检测业务语义。
- 新平台提供一个 GUI 产品入口。内部 runner/worker 可执行入口服务于运行和测试，不构成独立面向用户的 CLI 产品。当前 Python 图形界面继续维护，切换需完成各阶段验收。
- 延续未采集数据不得通过、自动结论与人工复核分离、凭据不进入日志和报告等要求。T110 等适用产品保留 [ADR-0002](0002-ground-heading-verification.md) 的航向互校要求，其他机器人定义对应的必需验证，不套用同一种运动流程。

详细约定见[总体技术方案](../design/mygo-plugin-platform.md)、[插件接口 v1](../design/plugin-api-v1.md)和[UI/UX 方案](../design/mygo-ui-ux.md)。

## 替代方案

- 每个产品修改并重编译主程序：实现初期直接，但产品交付与壳版本绑定，跨产品分支容易侵入通用流程。
- 仅用 YAML 表达全部检测：适合参数和步骤组合，无法覆盖新增协议、厂商 SDK 和专属算法。
- 所有插件都编译成独立原生程序：可以实现隔离，但普通配置和流程也承担三平台构建成本；采用脚本插件加可选辅助程序更适合当前目标。
- 在 GUI 进程中直接运行全部插件：宿主集成较轻，故障与设备操作生命周期难以独立管理。生产检测采用独立运行时与 worker。
- 继续以 NSH/Rust 为主线：技术上可实现同样的插件架构，但本次按桌面壳职责、插件开发方式和产品扩展需求选择 MyGo，不以已有代码量作取舍依据。

## 影响

[ADR-0001](0001-shared-core-and-product-profiles.md) 继续描述当前 Python 实现；新平台的入口和扩展方式以本决策为准。现有程序、配置、报告和发布方式不会因为文档状态改变而自动切换。

新增产品能否只安装插件取决于宿主是否已支持所需能力。原生 SDK、驱动与辅助程序仍须逐平台验证。脚本运行、进程隔离、设备停止与物理停稳分别提供证据，不互相替代。参考工程源码、资源和依赖的许可分别登记；UI 参考不等于已有源码复用授权或新界面验收。

# ADR-0001. GUI 与 CLI 共用检测核心和产品配置

## 状态

Accepted。现有仓库已具备共用结构；具体产品和产物能力仍以实际验证为准。

本记录继续描述当前 Python 实现。后续新平台的 GUI 入口、独立运行时和产品插件按 [ADR-0006](0006-mygo-plugin-platform.md) 实施；新方向尚未改变现有 GUI/CLI 行为。

## 背景

图形界面和命令行都需要执行车辆检测并生成报告。维护两份检测逻辑和阈值容易使同一车辆得到不同结果；产品型号又会有不同的话题、检测项和阈值。

## 决策

- 在同一仓库维护 GUI 和 CLI，两个入口共用检测执行、判定、探针、报告和产品配置，分别管理依赖和打包。
- 产品定义放在 `products/<产品id>/profile.yaml`，阈值放在同目录 `baseline.yaml`；按配置加载检测项，执行顺序必须符合 `static → runtime → motion`。
- 已支持的能力优先通过配置适配新产品；必需配置缺失应报出位置，不静默套用其他标准。新硬件、协议或检测能力可能需要代码开发。
- 动态检测模块或资源发生变更时，同时检查 GUI 和 CLI 的加载、打包及对应验证。

## 替代方案

- GUI 与 CLI 分仓维护各自核心：改动需要跨仓同步，判定和配置容易漂移。
- 产品差异硬编码在检测逻辑中：新增或调整型号需要修改代码，阈值更难核对。

## 影响

共享修改需要检查两个入口及其产物；配置校验只能验证已声明的结构和约束，不能证明车型适配或实车检测有效。

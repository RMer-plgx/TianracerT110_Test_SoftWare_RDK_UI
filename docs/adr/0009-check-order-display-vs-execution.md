# ADR-0009. 检测项的展示顺序与执行顺序解耦

## 状态

Accepted（2026-11-13）。待实施。

## 背景

`profile.yaml` 里的 `checks.items` 顺序**既是执行顺序，也是报告渲染顺序**。
而配置必须遵守 `static → runtime → motion` 的阶段约束
（`core/profile.py` 在加载时校验，顺序错了直接报错）。

于是 T110 的实际顺序是：

```
1,2,3,4,5,6,7,10,16,17,19   (static)
8,9,11,12,13,14,15,20       (runtime)
18                          (motion)
```

报告按 `results` 列表顺序渲染，所以读者看到的是：

```
1 2 3 4 5 6 7 10 16 17 19 8 9 11 12 13 14 15 20 18
```

**编号在纸上跳跃。** 用户的反馈原话是：

> 你的顺序不好从上到下应该一项一项的往下过，而不是这绿几个那黄几个

## 决策

**执行顺序与展示顺序分开。**

| 场合 | 顺序 |
| --- | --- |
| 实际执行 | 仍按 `profile.yaml` 的 `checks.items` 顺序，保持 `static → runtime → motion` |
| 报告 / GUI 卡片 | **按 `number` 升序 1..20** |
| 运行时提示 | 卡片上显示「正在检测第 N 项」，让用户知道真实执行序 |

### 为什么不能连执行顺序也改成 1..20

`static` 阶段不需要 bringup，`runtime` 需要，`motion` 会让车动。
三段之间有硬依赖：

- `runtime` 不能在 `static` 之前（还没验证网络/设备就打不开 SSH）
- `motion` 必须在 `runtime` 之后（需要 IMU/odom 数据才能互校）

如果按编号排序执行，第 8 项（IMU，runtime）会排在第 4 项（环境变量，static）
之前 —— bringup 还没起。所以执行顺序不能动。

### 报告里的排序怎么实现

`core/reporting.py` 渲染前对 `report.results` 按 `number` 排序，
**不修改原始列表**（`results` 的顺序仍是执行顺序，`raw.log` 按执行顺序记录）。

这样：

- 报告读者看到的是 1..20 连续
- 事后排查时 `raw.log` 仍是真实执行顺序
- 两者都对，不冲突

## 已一并确认：第 20 项前置到 runtime 最前

用户的设计初衷是「协议层数据应该在 IMU 和里程计之前采集，供它们使用」。
这需要把第 20 项在 `checks.items` 里从 runtime 末尾移到 `8` 之前：

```yaml
# runtime（新顺序）
- {number: 20, title: 通讯链路（协议层）, module: protocol, phase: runtime}
- {number: 8,  title: IMU,           module: imu,    phase: runtime, fatal: true}
- {number: 9,  title: 激光雷达,       module: lidar,  phase: runtime, fatal: true}
...
```

技术无障碍：第 20 项只读车上的 `/tmp/tap/*.raw`，不依赖任何 ROS 节点，
放在 runtime 最前反而更合理（bringup 刚起来，帧最干净）。

**注意**：前置后，第 20 项的「已采集但车上没有数据」会更容易出现，
因为 bringup 刚起时录音文件可能还没写满。实施时要把采集窗口从
「固定时长」改成「等到至少 N 帧或超时」。

## 替代方案

- **报告按执行顺序渲染（现状）**：编号跳跃，读者要来回找。不接受。
- **改编号让 execution 顺序就是 1..20**：会打乱历史编号，
  旧报告无法对照（`checks.items` 的注释写明「沿用历史编号，不重排」）。
- **报告里分组显示（static / runtime / motion 三个小节）**：
  能解释为什么跳跃，但读者仍然要跨小节找第 8 项。
  不如直接按编号排 + 卡片上标执行序直观。

## 影响

- 报告可读性提升，但**报告里的顺序不再等于执行顺序**。
  这一点要写进 `docs/product.md`，否则排查时会误判。
- `raw.log` 保持执行顺序 —— 需要，因为它是排查依据。
- 第 20 项前置后，它在报告里仍显示为「第 20 项」（编号不变），
  只是执行得早。

## 未验证

- 第 20 项前置后的采集窗口是否够。当前 `tap` 由 bringup 启动时创建，
  刚起来时写入的文件可能只有几百字节。需要实车确认：
  「bringup 就绪 + 第 20 项开始」之间的距离是否足以采到足够帧。
  如果不够，要把「采集 N 秒」改成「等到帧数达标或超时」。

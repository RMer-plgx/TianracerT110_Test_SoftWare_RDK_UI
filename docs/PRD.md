## 一、要解决的问题

### 1.1 背景

整车出厂前需要逐项验证：网络、传感器、底盘、运动、系统健康。
过去靠人工登录车上一条条敲命令、肉眼看输出、手工填表，问题有三：

1. **不可复现** —— 不同人测法不同，漏项是常态
2. **无留档** —— 测完只有一句"没问题"，出问题无法回溯
3. **判断依赖经验** —— "频率 29 Hz 算不算正常"没有客观标准

### 1.2 目标

> 输入一个 IP，自动跑完预设检测项，产出一份可交付、可追溯、
> 可人工复核的检测报告。

### 1.3 成功标准

| 指标 | 目标 |
|---|---|
| 单次完整检测耗时 | ≤ 12 分钟（不含落地运动） |
| 检测项覆盖 | 出货必检项 100% 覆盖 |
| 报告可追溯 | 每个数值都能在 `raw.log` 找到原始命令输出 |
| 误判率 | 已知误报场景全部有回归测试锁定 |
| 换产品 | 加新产品不改 Python 代码 |

## 二、用户与场景

### 2.1 主要用户

| 角色 | 场景 | 关心什么 |
|---|---|---|
| 出货检验员 | 每台车出厂前跑一遍 | 能不能发；报告能不能打印签字 |
| 研发/售后 | 现场排障 | 哪一项不对、原始数据是什么 |
| 产品负责人 | 汇总多台车质量 | 批量趋势，不关心单台细节 |

### 2.2 典型流程

```
车在一个陌生环境，没连网
  → USB-C 直连上位机（车机固定 192.168.128.10）
  → 软件自动让车连上与电脑相同的 WiFi
  → 读 WiFi IP，提示拔线
  → 拔线后用 WiFi IP 开始检测
  → 19 项跑完，出报告
  → 检验员在报告里逐条勾选人工项
  → 导出 PDF，签字归档
```

## 三、检测架构（核心章节）

### 3.1 当前实现：单层，全部在 ROS

**现状是单一数据源：ROS 话题。**

```
下位机 MCU ──串口──> tianbot_core ──ROS 话题──> 检测程序
                       (Node)                      │
                                                   └─ 只看到这一层
```

`checks/` 下 19 项的手段清点：

| 手段 | 数量 | 层次 |
|---|---|---|
| `rostopic` / `rosnode` / `rosservice` | 主要 | ROS |
| 下发 probe 脚本在车上跑 | 6 项 | ROS |
| `ls -l /dev/*` | 1 项 | 文件系统 |
| `udevadm info` | 1 项 | 设备元信息 |
| `lsof`（仅提示文案） | 0 项实际执行 | — |
| **直接读串口字节流** | **0 项** | **—** |

### 3.2 这个架构的固有缺陷

**关键认知：ROS 层看不到"数据为什么没有"。**

以电池电压为例（2026-11-06 实际发生）：

```
物理层   电池有电（车能正常行驶）              ✅
协议层   下位机有电压字段 Battery_voltage      ✅
ROS 层   /tianracer/voltage 话题从不发布        ❌
```

`chassis.cpp` 只处理 `PACK_TYPE_Voltage_RESPONSE`，但**没有任何代码发起查询**。
于是话题 advertise 了却永远无数据，检测程序判"读不到电压"。

站在 ROS 层，以下三种情况**表现完全相同**：

| 真实原因 | ROS 层看到 |
|---|---|
| 下位机根本没收到查询 | 无数据 |
| 下位机回了，但包被丢弃 | 无数据 |
| 下位机回了，但解析失败 | 无数据 |

三者排查方向完全相反（查请求逻辑 / 查链路 / 查协议解析），
但报告只能写"无数据"，把排查成本推给了下一个人。

### 3.3 缺陷的第二个来源：静默降级

ROS 层还有个更隐蔽的问题：**数据看起来"有"，但不代表"对"**。

已发现实例：

| 现象 | ROS 层看不出 | 后果 |
|---|---|---|
| 串口 termios 配置错误（`\|= ~(...)`） | 话题照发，但帧被截断 | BCC error 刷屏，IMU 频率掉到 44 Hz 仍判"接近阈值" |
| 雷达与底盘抢同一串口 | `/dev/tianbot_lidar` 存在 | bringup 反复重启，报错指向串口而非配置 |
| 电压从不发布 | 话题存在、类型正确 | 只能判"无数据"，无法定位到"没人发请求" |

### 3.4 目标架构：双通道

> **这是本 PRD 最重要的改进项。**

```
                    ┌──> ROS 话题 ──────> 语义层检测（现有 19 项）
下位机 MCU ──串口──> │
                    └──> 协议帧旁路 ────> 链路层检测（新增）
```

**双通道的设计原则：**

1. **ROS 通道不动** —— 现有 19 项判定逻辑、报告格式、回归测试全部保留
2. **协议通道只读** —— 旁路监听，不参与控制，不写串口（除显式查询）
3. **两通道独立判定** —— 协议层异常时，ROS 层结论要降级为"不可信"而非"通过"

**协议通道能回答 ROS 层答不了的问题：**

| 问题 | ROS 层 | 协议层 |
|---|---|---|
| 下位机在发心跳吗？ | 看不到 | ✅ 心跳计数、间隔、固件版本 |
| 电压为什么不报？ | 无数据 | ✅ 是没请求、还是没响应、还是响应异常 |
| 帧校验失败率多少？ | 看不到 | ✅ BCC 错误率、重传次数 |
| IMU 数据是原始值还是滤波后？ | 不知道 | ✅ 原始帧 vs 话题值对比 |
| 串口物理链路质量 | 看不到 | ✅ 帧间隔抖动、超时次数 |

**协议层判定示例（电压）：**

```
场景 A：发了 10 次查询，0 次响应
  → 结论：下位机未响应，查固件或链路
场景 B：发了 10 次查询，10 次响应，但话题无数据
  → 结论：tianbot_core 解析/发布环节故障，查 ROS 侧
场景 C：从未发出查询
  → 结论：tianbot_core 缺少主动查询逻辑（当前实际情况）
```

三种情况给出三条完全不同的排查路径 —— 这才是"完备"。

### 3.5 协议层实现的已知约束

| 约束 | 说明 |
|---|---|
| 串口独占 | `/dev/ttyUSB0` 已被 `tianbot_core` 占用，旁路需要只读复用（`TIOCSTI` 不可行，需用 `socat` 或让 core 支持 tee） |
| 需要结构体定义 | `protocol.h` 目前只确认了包类型枚举与帧格式，字段偏移待补全 |
| 需要请求包格式 | 电压、心跳的查询命令码未知 |
| 不能影响正业 | 旁路采集失败必须静默降级为"仅 ROS 层"，不能让整轮检测失败 |

## 四、检测项

### 4.1 分层

| 层 | 编号 | 含义 |
|---|---|---|
| static | 1-7, 10, 16, 17, 19 | 不需要 bringup，无风险 |
| runtime | 8, 9, 11-15 | 需要 bringup |
| motion | 18 | 会让车动，必须人工确认 |

**执行顺序即依赖顺序**，配置加载时强制校验 `static → runtime → motion` 不回退。

### 4.2 清单（Tianracer T110 RDK，19 项）

| # | 项 | 层 | 致命 | 判什么 |
|---|---|---|---|---|
| 1 | 网络连通性 | static | ✅ | SSH 可达、延迟 |
| 2 | 系统身份 | static | | 主机名、内核、OS、ROS 版本 |
| 3 | RustDesk 远程桌面 | static | | 服务状态、图形会话 |
| 4 | 环境变量 | static | | 与产品配置比对 |
| 5 | 设备节点 | static | | 必需设备存在、软链指向 |
| 6 | 主控硬件 ID | static | | CP2102 序列号 |
| 7 | 源码一致性 | static | | 仓库未提交改动 |
| 8 | IMU | runtime | ✅ | 频率、静止角速度、姿态 |
| 9 | 激光雷达 | runtime | ✅ | 频率、点数、有效比例 |
| 10 | 雷达以太网 | static | | 可达、丢包、延迟 |
| 11 | USB 摄像头 | runtime | | 分辨率、编码、频率 |
| 12 | 里程计 | runtime | ✅ | 频率、静止漂移 |
| 13 | TF 树 | runtime | | frame 连通性 |
| 14 | 电池电压 | runtime | | 电压值 |
| 15 | 激光建图链路 | runtime | | gmapping 起得来、地图参数 |
| 16 | teb 导航插件 | static | | 插件注册、地图存在 |
| 17 | 系统健康 | static | | 温度/磁盘/负载 |

| 19 | 使用痕迹 | static | | 日志/历史体积 |

### 4.3 每项的判定要求

**必须满足三条：**

1. **有具体数值** —— 「通过」后面要列出实测值，不能只写「正常」
2. **不通过时点名** —— 「负载 3.50 超过警告线 3.0」，不能写「指标接近阈值」
3. **取不到数据 ≠ 合格** —— 无数据判 SKIP，不计入通过

## 五、判定规则

### 5.1 状态

| 状态 | 含义 | 计入通过 |
|---|---|---|
| PASS | 通过 | ✅ |
| WARN | 告警，需人工判断是否可接受 | ❌ |
| FAIL | 失败，不可通过勾选覆盖 | ❌ |
| SKIP | 完全未执行 | ❌ |
| PENDING | 已测一部分，结论待后续阶段 | ❌ |

### 5.2 交付判定（按优先级）

```
1. 中途停止                          → 不具备交付条件
2. 任何 FAIL                         → 不具备交付条件
3. 致命项停在 PENDING                → 不具备交付条件
4. 未验证比例（SKIP+PENDING）> 20%   → 不具备交付条件
5. 有未验证项但在 20% 内             → 可交付，但需确认
6. 全 PASS                           → 具备交付条件
```

**第 3 条的含义（重要）：**

IMU 与里程计的航向精度必须落地转圈互校才能确认。
不勾「完整运动测试」时它们停在 PENDING，**整机判不可交付**。

这是有意的：航向精度从未验证的车不该判合格。
场地不允许时，只能在报告里人工勾选「确认接受」，
但**程序自动判定保持红色**，两者并存不覆盖。

### 5.3 人工复核

- 告警项可在 HTML 报告里逐条勾选「确认接受」
- 勾选后转绿、计入通过数
- **不改 `Report.verdict`** —— 程序判定与人工复核并存
- 所有勾选动作记入「复核记录」，带时间戳

## 六、报告

### 6.1 产物

每轮检测生成一个目录：

```
test records/<IP>_<YYYYMMDD_HHMMSS>/
├── report.html              交互式报告（可勾选、可导 PDF）
├── report.md                纯文本版本
├── raw.log                  每条命令的原始输入输出
├── jspdf.umd.min.js         PDF 导出依赖（随报告走）
└── html2canvas.min.js
```

### 6.2 要求

| 要求 | 理由 |
|---|---|
| 每个数值可追溯 | 排查时能看原始命令输出 |
| HTML 自动转义 | 车辆输出可能含 `<script>` |
| PDF 一键下载 | 出货人员要打印签字 |
| 版本号入报告 | 拿到报告能反查是哪版软件 |
| 产品名入报告 | 多产品后必须能区分 |

### 6.3 PDF

用 jsPDF + html2canvas 在报告内直接生成，不再跳打印界面。
两个库复制到报告目录旁，相对引用 —— 报告文件夹可整体打包发人，离线可用。

## 七、多产品架构

### 7.1 结构

```
products/
├── _template/              新产品模板（可加载通过）
│   ├── profile.yaml
│   └── baseline.yaml
└── tianracer_t110_rdk/     首个产品
    ├── profile.yaml        产品定义：话题、工作区、检测项清单
    └── baseline.yaml       判定阈值
```

### 7.2 硬性要求

| 要求 | 说明 |
|---|---|
| 加产品不改代码 | 复制模板改配置即可 |
| 不做静默兜底 | 缺字段抛错并指出文件+字段 |
| 顺序校验 | `static → runtime → motion` 不回退，加载时强制 |
| 阈值唯一来源 | 只有 `products/*/baseline.yaml`，不存在第二份 |

### 7.3 缺字段为什么必须报错

代码里有 `cfg.get("x", 默认值)`。如果配置漏写就走默认值，
检测会安静地按另一套标准跑，报告看起来正常但结论是错的。
**崩溃会被发现，静默跑偏不会。**

防线：`BASELINE_REQUIREMENTS` 声明式校验，
按启用的检测项检查必需键，一次报出所有缺失项。

## 八、连接方式

### 8.1 有线模式

用于车在陌生环境未联网时。

```
1. 检测上位机 192.168.128.10 可达
2. 读车上 WiFi 状态
   └ 已连着与电脑相同的网络 → 跳过重连
3. 需要重连 → 扫描 → 匹配 SSID → 需要密码则弹窗
4. 读 WiFi IP → 提示拔线
5. 检测到拔线 → 用 WiFi IP 开始检测
```

### 8.2 无线模式

车已在 WiFi 上，直接填 IP。

### 8.3 必须如实告知的事

有线模式会**在车上创建持久化 WiFi 配置**
（`/etc/NetworkManager/system-connections/<SSID>`，含密码，默认自动连接）。
这与「只读检测」不同，UI 在开始前必须明确提示，并给出清理命令。

## 九、质量保障

### 9.1 测试分层

| 层 | 目的 | 现状 |
|---|---|---|
| 单元测试 | 判定纯函数、配置加载、模板渲染 | 312 项 |
| 全项 smoke | 19 项逐个 run，任何异常即失败 | 有 |
| AST 静态检查 | 调用点参数个数、硬编码话题 | 有 |
| 实车验证 | 真实硬件、真实异常 | 每版必做 |

### 9.2 必须存在的防线

以下每一条都对应一次真实事故，**不得删除**：

| 防线 | 防的是什么 |
|---|---|
| 全 19 项 smoke | 接口改动导致某检测项 TypeError，而测试全绿 |
| AST 扫 `core.remote` 调用点 | 漏传 profile 参数被 `except` 吞掉 |
| `start_launch` 参数个数校验 | 机械替换留下的多余参数，日志都不生成 |
| 版本号 ↔ CHANGELOG 一致 | 改完版本忘了写 CHANGELOG |
| 报告 HTML 转义 | 车辆输出注入 `<script>` |
| SSID/密码 shell 转义 | 命令注入 |

### 9.3 中文 Windows 专项

`netsh wlan show interfaces` 的中文输出里有三行都含「状态」
（状态 / 无线电状态 / 承载网络状态）。子串匹配会让最后一行赢，
导致 WiFi 明明连着却判成断开 —— 有线模式 100% 失败。

必须按**行首键名**匹配，且先排否定词再认肯定词
（`disconnected` 里含 `connected`）。

## 十一、已知缺陷与改进计划

### 11.1 P0 — 检测不完备（本 PRD 核心改进项）

| 缺陷 | 影响 | 计划 |
|---|---|---|
| 全部检测站在 ROS 层 | 无法区分"没请求/没响应/解析失败" | 双通道架构（§3.4） |
| 电压话题从不发布 | 第 14 项永远失败 | 协议层确认是缺请求还是缺响应 |
| 串口配置错误只能靠频率异常间接发现 | 排查绕远路 | 协议层直接统计 BCC 错误率 |

### 11.2 P1 — 车端配置依赖

| 问题 | 现状 | 建议 |
|---|---|---|
| udev 规则型号不匹配 | 摄像头 `32e6:9221` 不在规则里 | 固化到出厂镜像 |
| 雷达 `lidar_serial` 写死 `ttyUSB0` | 与底盘抢串口 | 改车上 launch 文件 |
| `devel/setup.bash` 错误默认值 | 覆盖 `~/.bashrc` 正确值 | 修 env-hooks |

### 11.3 P2 — 体验

- PDF 跨页时表格可能被截断（长图切片的固有限制）
- 有线模式失败后的回滚路径不够清晰

## 十二、不在范围内

明确**不做**的事，避免范围蔓延：

- 不修改车辆持久配置（连接 WiFi 除外，且必须提前告知）
- 不替代人工判断（遥控手感、建图效果等仍需人看）
- 不做长时间稳定性测试（只做短时采样）
- 不做性能压测
- 不实现 OTA 或固件升级

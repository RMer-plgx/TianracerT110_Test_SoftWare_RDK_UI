# 产品说明

后续产品目标已扩展为不同类型机器人的插件化检测平台，允许通信协议、检测流程和专属交互不同。采用 MyGo 桌面壳，架构与 UI/UX 参考 `mygo-music`；详细设计与分阶段验收见[技术方案](design/mygo-plugin-platform.md)。该平台尚未实现，下文的入口、检测清单、耗时目标和已知问题仍描述当前 Python/T110 范围。

tb-verify 用于车辆出厂检测：通过图形界面连接车载上位机，按产品配置执行检测，生成可供人工复核、导出和归档的报告。当前默认产品为 Tianracer T110 RDK，检测项由产品配置决定。架构现状及决策见[架构总览](adr/README.md)。

## 用户与流程

出货检验员关注检测结论、人工项和报告归档；研发和售后关注故障定位与原始数据；产品负责人需要跨车辆汇总质量。批量趋势仍是需求，不能视为已有能力。

车辆已联网时使用无线模式输入 IP；未联网时可通过 USB-C 连接车载上位机（`192.168.128.10`），配置 Wi-Fi、取得无线 IP，再断开有线连接进行检测。连接和检测可能修改车端状态：Wi-Fi 配置可能持久保存，自动运行模式可能启停 ROS，清理使用记录会删除车端数据。

## 产品目标

| 目标 | 验证方式或边界 |
| --- | --- |
| 单次完整检测不超过 12 分钟 | 不含落地运动；需在目标产品和环境测量 |
| 覆盖全部出货必检项 | 按产品逐项确认必检清单与覆盖证据 |
| 检测结果可追溯 | 保存采集证据、本地计算来源和人工复核记录；当前有缺口，见[复核与证据方案](adr/0003-review-and-evidence.md) |
| 已知误报场景有回归测试 | 按场景确认测试覆盖；测试替身不代表实车验证 |
| 适配多个产品 | 已支持的能力优先通过配置适配，新能力可能需要代码 |

以上是目标，不代表已完成验收。

## 检测阶段

| 阶段 | 检测项编号 | 说明 |
| --- | --- | --- |
| static | 1–7、10、16、17、19 | 不依赖 bringup |
| runtime | 8、9、11–15、20 | 依赖 bringup |
| motion | 18 | 涉及运动，须人工确认并保留停车和清理路径 |

执行顺序由配置指定，加载时校验阶段不回退。涉及实车连接、运动或修改车辆配置的操作须事先获得明确授权。

## 判定与复核

检测结果应给出实测值、阈值和异常原因；未取得的数据不能计为通过。自动判定和人工复核分开展示。当前自动判定在中止、FAIL、致命项 PENDING 或未验证比例超过 20% 时不能判为具备交付条件；WARN 或容忍比例内的未验证项需要确认。无数据在不同检测项中的状态尚不统一，当前电压项无有效数据时可能判 FAIL。

## 已知问题与待验证事项

- 底盘运行数据主要来自 ROS。已确认下位机会主动低频上报电压（一次 20 秒架空采集见 3 帧），ROS 短窗口订阅可能漏采，无有效值不等于硬件异常。协议观测方案及证据边界见 [ADR-0004](adr/0004-protocol-observation.md)。
- 车端配置可能存在摄像头 udev 规则、雷达串口配置或 ROS 环境变量问题；具体车型、镜像和现场状态需要核实。修改车端配置须授权。
- **转向角读不到**（MCU 无角度回传帧），只能靠「恒定转角 + IMU 角速度」间接反推；换车或换舵机后需重测。（2026-11-10 完成首次标定，见 [ADR-0005](adr/0005-steering-calibration.md)）
- **四驱同速使转弯必然打滑**（几何理论 29%，实测 28%~35%），「转一圈回原点」在本车型上物理上不成立，闭合误差只记录不判定。
- 有线连接失败后的回滚路径需要完善。
- 中文 Windows Wi-Fi 状态解析应按行首键名匹配，先排除否定词，避免误判。
